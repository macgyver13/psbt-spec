PSBT Conformance Specification

Status: Draft. Rule IDs may change until version 1.0.

Covers PSBT versions 0 and 2 (BIP174, BIP370) with the extensions of BIP371, BIP372 (Draft), BIP373, BIP353, BIP322, BIP375 and BIP376, as written at bitcoin/bips 5aadddb, except BIP375, which is pinned at 9c5b825e4b. A PSBT is well formed if it satisfies the General rules. A role conforms if its rules hold on the PSBT it received and the PSBT it returned. Each statement keeps its BIP's MUST, SHOULD or MAY and links its source. A rule marked Derived or Resolution is the project's reading, not BIP wording, and says why.

Silent payments: BIP375 covers sending to a silent payment address with a PSBT, and BIP376 covers spending a silent payment output. Both build on BIP352 (silent payments) and BIP374 (DLEQ proofs); the silent payment terms are in Definitions.

Verified
The check found the property holds.
Failed
The check found it does not; the rule's ID is the error code.
NotApplicable
The statement does not apply to this PSBT.
Incomplete
The PSBT lacks the context to decide; this is not a pass.
Full
Coverage: the check decides the stated property whenever the PSBT carries the context it needs.
Partial
Coverage: it decides part of the property; the implementation note says what it leaves undecided.
Declared
Coverage: this reference cannot decide it, because it needs cryptography the reference does not carry or behavior a PSBT does not show.
Pending
Coverage: there is no check yet.
Derived
Basis: the rule follows from BIP text but does not restate one sentence; it merges sentences, or reads a requirement from a field description or another BIP. An unmarked rule restates one BIP sentence.
Resolution
Basis: the BIP text is ambiguous or silent, and the project decided; the reading gives the basis.

Evaluate your project

A project judges its own compliance by rule ID. psbt-spec evaluate puts every corpus vector to the project through an adapter and writes a report with one verdict per rule and operation. psbt-spec attribute reads a PSBT, with the task that produced it, and lists the rules it fails.

To run an evaluation, build psbt-spec from source and point it at your adapter and one or more corpus files:

git clone https://github.com/macgyver13/psbt-spec
cd psbt-spec/rust
cargo run --release --bin psbt-spec -- evaluate --out DIR \
    --corpus ../vectors/roles.json --corpus ../vectors/bip375.json \
    -- ADAPTER [ARGS ...]

The report is written to DIR/report.json and DIR/report.md. Each row gives one verdict for a rule at one task:

MATCH
The project accepts and rejects what the rule does. A MATCH from a refusal that named no rule is marked unconfirmed.
STRICTER
The project rejects something the rule accepts.
LOOSER
The project accepts something the rule rejects, or has no check.
NOT IMPLEMENTED
The project does not declare the task or BIP the vectors need.
NOT RUN
No vector gave evidence: the corpus has none for the rule, or the project answered n/a or failed. NOT RUN is not a pass.
  • Adapter contract: the JSON lines an adapter reads and answers.
  • Report format: verdicts and how they are decided.
  • The attribute command: which rules a PSBT fails.
  • Example adapters: bip375-reference (Python, 138 lines), rust-psbt (Rust, 325 lines) and spdk (Rust, 265 lines). A minimal adapter is a loop of a few dozen lines; see the skeleton in the adapter contract.

This page publishes no project's results. Cross-implementation results are seen in the interoperability harnesses: bip375-interop-v2 and psbt-interop-lab.

Each rule's Check column shows its corpus coverage: the invalid vectors that isolate it, the valid vectors that pass it, and a status. corpus: a vector isolates the rule, so evaluate judges projects on it. tests only: no vector isolates it yet; its check is observed failing only by the repository's tests. none: the rule has no check. Vectors are numbered from 0 within their file.
